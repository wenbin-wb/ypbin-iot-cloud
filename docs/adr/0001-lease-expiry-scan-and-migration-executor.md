# ADR-0001 · 租约失效扫描与数据库迁移的「执行者」问题

- 状态：**已接受**（M0a 落地；M0b 有明确的必办动作）
- 日期：2026-09-19
- 上下文依据：`IOT-CLOUD-SPEC.md` §3.1①（失效检测）、§4.2（部署单元② 无状态多副本）、§12.2（数据库迁移）

---

## 1. 要解决的问题

`business` 是**无状态多副本**部署单元（§4.2），而它有两件事天然带「只能有一个执行者」的味道：

| 事项 | 出问题的形态 |
|---|---|
| **租约失效扫描**（§3.1①） | N 个副本各自「读出一批过期租约 → 逐个改状态」。多副本并发下会重复处理、重复写；若将来带上「发事件/发通知」的副作用，就会重复通知 |
| **数据库迁移**（§12.2） | N 个副本同时跑 Flyway → 并发迁移，轻则报错、重则半途改坏 schema |

M0a 还没有台账表（迁移在 M0b 定稿），但**这两条决策必须在 M0a 定死**：它们决定了 M0b 的表结构与应用启动流程，事后改代价远大于现在写清楚。

## 2. 决策

### 2.1 租约失效扫描：M0a 进程内，M0b 改成「单条原子 UPDATE」

- **M0a（现在）**：`core` 的 `LeaseExpiryScanner` 用 `@Scheduled` + **内存** 归属表（`InMemoryLeaseStore`）扫描过期租约并置为 `PENDING_TAKEOVER`。
  - 前提写清楚：**M0a 的归属状态不跨副本共享**，因此这份实现只在「单 business 副本」下语义完整。
  - 语义部分（谁过期、置成什么状态、接管要不要递增 epoch）全部在 `LeaseService` 里，与调度器和存储解耦，M0b 换存储时**判定逻辑不用重写**。
- **M0b（必办）**：扫描改成**一条原子语句**，不做「读列表 → 循环 → 写回」：

  ```sql
  UPDATE tenant_node_assignment
     SET state = 'pending_takeover'
   WHERE state = 'active'
     AND lease_expire_at < NOW();
  ```

  - 原子性由数据库保证：N 个副本同时执行也只会各改到自己那一批，不会互相覆盖；
  - 需要「恰好一次副作用」（例如发事件、写审计）时，**不要**靠应用层去重，而应让数据库**返回受影响行**（或 `RETURNING`/“选中并加锁”），拿到行的那个副本才有资格产生副作用；
  - 若将来需要严格的单执行者，用**租约式的调度锁**（专门一行锁记录 + `SELECT ... FOR UPDATE` / 带过期时间的 leader 行）——不要用「启动时抢一次」的内存标记，副本重启就失效。

### 2.2 数据库迁移：一次性作业执行，`business` 永不执行迁移

- 迁移由**一次性迁移作业**执行（§12.2）：
  - compose 形态：独立的一次性 service，`restart: "no"`，应用服务 `depends_on: { db-migrate: { condition: service_completed_successfully } }`；
  - k8s 形态：Job / initContainer；
  - 应用服务一律 `spring.flyway.enabled=false`。
- **schema 版本校验**（应用启动时）：`actual < expected` → **拒绝启动**；`actual > expected` → 允许启动 + 告警（否则「先迁移、后滚动发布」这条路直接走不通）。`expected` 必须由**构建期从 `deploy/sql` 生成常量**，并配漂移门禁——手抄必然漂移。
- 迁移必须**向后兼容**（先加不改不删、双写过渡），破坏性变更拆两次发布；社区版 Flyway 没有 undo，回滚靠「向前修复 + 备份恢复」。

## 3. 为什么不让 `business` 迁移（而不是「加把锁就行」）

- `business` 会**滚动升级**：迁移期间新旧副本并存，谁先启动谁迁移会导致「老代码跑在新 schema 上」的窗口不可控；
- 迁移是**部署动作**，不是业务动作：它需要「先备份再迁移、失败即停」的顺序保证，这些不属于应用进程的职责；
- 把迁移放进一次性作业后，「迁移 → 校验 → 再启动应用」的次序由部署编排保证，**应用侧只剩只读的版本校验**。

## 4. 影响与遗留

| 影响 | 说明 |
|---|---|
| M0a 不能多副本跑 business | 归属状态在内存里、不共享。验收（P3/P5）都在单副本形态下进行 |
| `business` 需要 `@EnableScheduling` | 扫描器由 core 提供，调度开关在 business 启动类上（避免库模块自己开全局调度） |
| M0b 必办清单 | ① 建 `tenant_node_assignment` 表并把 `InMemoryLeaseStore` 换成数据库实现（保留 `LeaseService` 的判定逻辑）；② 扫描改原子 UPDATE + 受影响行驱动副作用；③ 迁移作业 + schema 版本校验 + `deploy/sql` 漂移门禁 |

## 5. 未采纳的选项

| 选项 | 不采纳的原因 |
|---|---|
| 让 `business` 用 `spring.flyway.enabled=true` 各自迁移 | 多副本并发迁移不可控；滚动升级期间新老代码与 schema 的交错无法推理 |
| 应用层「谁先启动谁扫描」的内存标记 | 副本重启即失效；多副本下退化为「都不扫」或「都扫」，比单副本更糟 |
| 把失效判定放进 `access`（谁采集谁检测） | 旧节点若是长 GC/网络分区而进程仍活着，它不会承认自己过期（§3.1① 的 self-fencing 正是为此），必须有第三方视角 |
| M0a 直接上数据库表 | M0a 不接 DB 是既定边界（§10），提前引入会把迁移形态的决策绑死在未评审的表结构上 |
